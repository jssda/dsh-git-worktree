## Reproduced failures and verified root causes

The first focused run reproduced both handoff failures with real Cordis Loader and Web registry:

1. Live replacement disable left `graph=[]` instead of `[official]`, even after the existing `vi.waitFor` timeout.
2. Failed replacement activation left `[official, worktree]` instead of `[official]`, even after explicitly awaiting the activation fiber.
3. The apparent teardown `PrettyFormatPluginError` was the final slow-disable test trying to format a retained Cordis fiber during `expect(official.fiber).toBeUndefined()`. Loader 1.0.6 retains this reference; Cordis Context rejects pretty-format's uninjected `$$typeof` lookup. After fixing production, both graph tests passed while this error remained. Replacing the stale object-shape assumption with the real public disposal condition (`fiber.uid === null`) made the remaining test pass. No errors were swallowed and no teardown cleanup was disabled.

Inspected **only the newly installed** package implementations and declarations:

- `@deepseek-ai/cordis-plugin-loader@1.0.6/lib/index.js:361-391`: `refresh()` immediately returns whenever `entry.fiber` exists; disabled `update()` schedules `fiber.dispose()` without awaiting it; enabled `update()` can initialize a new generation when the old uid is cleared. `init()` is public (`lib/types/config/entry.d.ts:56`), and `fiber?: Fiber` is a public writable field (`:25`).
- Loader `lib/index.js:429-465`: `init()` schedules activation; the fiber owns its settled outcome. Loader `await()` tracks import/lifecycle work (`:150-160`).
- `@deepseek-ai/cordis@4.0.5/lib/index.js:1351-1403`: failed apply unloads effects without clearing the fiber uid; `_unload()` uses `Promise.all` over effects, so registration order is not sequential LIFO teardown. The declaration at `lib/types/fiber.d.ts:67-74` confirms `UNLOADING=5`; no new numeric state was guessed.
- `@deepseek-ai/dsh-client-modules@0.2.1-rc.2/lib/index.js:545-557,851-860`: the registry dirties names on `internal/plugin` and includes enabled entries whenever `entry.fiber` exists, without checking uid/FAILED state. There is no public rescan method for arbitrary lifecycle changes.

### Production changes this round

At `src/workspace-provider-lifecycle.ts:66-101`, the existing bounded/in-flight operation now waits for the captured disabled fiber's lifecycle, rather than just the scheduling promise. Restore uses public `entry.init()` when `uid === null`; otherwise it retains `refresh()`. No raw disabled flags are changed.

At `src/workspace-provider-lifecycle.ts:124-153`, cleanup explicitly awaits the idempotent marker disposer before checking the official expression. It withdraws only the **identical owning replacement entry/fiber reference**, then emits the owning `internal/plugin` event consumed by the registry. Disposed fibers can withdraw immediately. A still-live fiber is withdrawn only when its eventual `await()` rejects, not on successful same-fiber restart. That wait is deliberately not awaited inside its own disposer (which would self-deadlock). Root/Include unload guards and the per-entry in-flight guard prevent resurrection or overlapping Loader mutation.

This narrow writable-Entry/registry-notification compatibility boundary was explicitly escalated and approved by the parent before implementation. No Host dependency source, Web registry implementation, user Profile or persistence behavior was patched. Future upstream changes to this boundary require renewed review.

### Focused regression coverage

`tests/workspace-provider-lifecycle.test.ts:166-234` now covers five consecutive disable/re-enable changes, actual new fiber identities, no official-options mutation and no tree write, a successful same-fiber `restart()`, concurrent disable/re-enable while the old generation cleans up, and failed activation restoring the sole official graph while leaving replacement configuration enabled and clearing its stale reference/marker. Existing tests retain root disposal, both boot orders, disabled owning groups, market replay, delayed imports/Includes, explicit user overrides, timeout and slow-operation cases (`:234-290`). No test was skipped, arbitrary wait increased, or graph assertion weakened to hide a production failure.

The slow-disable fixture's final assertion (`:286-289`) now checks the public disposed uid, not absence of the old Loader reference; its final **exactly `[worktree]`** graph assertion remains. The new concurrency fixture was initially drafted with direct `fiber.dispose()` on an enabled entry and failed because Loader intentionally persists a disable for that user action (23 passed / 1 failed); a targeted diagnostic confirmed the new uid/marker survived but the entry was disabled. The corrected fixture uses actual disabled/enabled `entry.update()` calls, exercising the production path without overriding persistence or changing production code. Final focused and complete checks were then rerun, all passing.

The pre-existing never-settling fixture deliberately expects both rows while the fake official operation refuses to settle: it proves startup is not held hostage, not successful election. Timeout is not cancellation. Normal settled disable/failure paths now assert exactly one provider; a permanently wedged upstream operation remains a residual limitation rather than an unconditional no-overlap guarantee.
